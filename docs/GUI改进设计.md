# 桌面端界面改进设计

> 起因：用户反馈「是不是少了 K 线图类的主图、模拟交易的细节、主图、交易分析报告」，
> 并要求先看看专业工具是怎么做的。
>
> 本文是**先搜依据、再对现状**的结论，不是凭印象列的清单。

## 一、专业工具的标准做法（搜到的共识）

对照了量化回测平台（Backtrader-PyQt-UI、backtest-kit）与回测结果阅读指南，
它们收敛到**同一套三区布局**与**同一组必看指标**：

### 布局：三区

| 区 | 内容 |
|---|---|
| **左：配置区** | 策略选择、参数调整、资金管理、运行按钮 |
| **中：图表区** | **主 K 线图**（蜡烛 + 均线叠加）→ 下方 **成交量柱** → **买卖点标记**；副图为 RSI/MACD 等 |
| **下：结果区** | 绩效统计 + **净值曲线** + **逐笔交易明细表** |

### 报告：必看的指标（多来源一致）

| 指标 | 判读基准 |
|---|---|
| **Profit factor**（总盈利 ÷ 总亏损） | >1.5 良好，>2.0 优秀，<1.0 亏钱 |
| **Expectancy**（每笔期望收益） | 必须为正；>0.25R 算强 |
| **Win rate**（胜率） | **单独看没有意义**，必须与盈亏比一起看 |
| **平均盈利 / 平均亏损** | 构成上面两个 |
| **Max drawdown** + **回撤持续时间** | 决定"心理上能不能扛" |
| **最大连续亏损笔数** | 决定要准备多少缓冲 |
| **Sharpe / Sortino / Calmar** | 风险调整收益，做版本对比用 |
| **成交笔数** | <100 统计不可靠，300+ 才有信心 |

### 报告还应该**主动标出的红旗**

- 成交笔数 < 20 → 样本不足，什么都说明不了
- 少数几笔贡献了大部分利润 → 可能是运气而非优势
- 亏损笔显著大于计划 → 风控失效
- 收益异常平滑/一致 → 可能过拟合了某段行情

> ⭐ 有一条值得单独记：多篇资料都强调
> **「只有聚合统计、没有逐笔明细的回测报告，是一个无法追问的结论」**
> —— 而逐笔明细正是调试策略最有用的工具。

## 二、现状盘点（实际去代码里看的）

**已有（比想象的多）**：

| 现有页签 | 内容 |
|---|---|

## 三、缺口清单（正是用户提的四点）

| # | 用户提的 | 现状 | 缺口 |
|---|---|---|---|
| ① | **K 线主图** | `c_price` 是**折线**（中间价 + 基本面锚） | **没有蜡烛图** |
| ② | **模拟交易细节** | 只有聚合指标（capture/drift/n） | **没有逐笔明细表** |
| ③ | **主图** | 同上（折线而非 OHLC） | 需要 OHLC + 成交量 + 买卖点 |
| ④ | **交易分析报告** | 有 markout/capture/drift，但这些是**做市专用**指标 | **缺经典绩效指标**（盈亏比 / 期望值 / 胜率 / 最大连亏 / R 分布）+ 红旗提示 |

### 好消息：三个缺口都不用动引擎

- **OHLC**：`series.mid` 已经逐 tick 传到前端了，**在前端聚合**即可
  （或后端加一个 `_ohlc(series, window)` 纯函数，二选一）
- **逐笔明细**：`log.trades` 与 `collect_fills` 都在，**只需暴露到 API**
- **绩效指标**：都能从逐笔成交 + 权益曲线**算出来**，不需要新的模拟

## 四、建议方案

### 主图改造（页签「图表」→ 第一张图升级）

```
┌────────────────────────────────────────────┐
│ 价格主图（蜡烛）                             │
│  · OHLC 从 series.mid 按窗口聚合             │
│  · 叠加：基本面锚（虚线）、均线（可选）        │
│  · 标记：策略成交点（▲买 ▼卖）                │
│  · 图例可切换：红涨绿跌 / 绿涨红跌 ★          │
├────────────────────────────────────────────┤
│ 成交量（与主图共享 x 轴）                     │
└────────────────────────────────────────────┘
```

★ **红涨绿跌 vs 绿涨红跌**：这是加密市场（国际惯例绿涨红跌）与中国用户习惯
（红涨绿跌）的冲突。建议**默认红涨绿跌**并**提供一键切换**——
专业工具都有这个开关，不给开关才是问题。

### 新增页签「成交明细」

每行：`tick | 方向 | 价格 | 数量 | 对手方 | markout(h) | 该笔盈亏 | 累计盈亏`
- 可排序、可导出 CSV（导出能力已有：`/api/export/<id>.csv`）
- 点击某行 → 主图定位到那个 tick（专业工具都这么做）

### 新增页签「分析报告」

- **指标卡**（一行）：盈亏比 / 期望值 / 胜率 / 最大回撤 / 最大连亏 / 成交笔数
- **R-multiple 分布图**：每笔盈亏 ÷ 初始风险
- **红旗区**：按第一节的判据自动提示——样本不足、利润集中、回撤过大
- ⚠️ **这些指标要标注口径**（本项目的一贯纪律）：
  例如「盈亏比」在**做市策略**上需要说明"笔"是单笔成交还是完整回合；
  「胜率」对做市策略尤其容易误导（赚价差 vs 接刀是两件事，
  项目已有 `markout` 分开这两者）。**别把经典指标直接套在做市策略上就宣称有效。**

## 五、工作量与取舍

| 项 | 改动 | 量级 |
|---|---|---|
| OHLC 聚合 | 后端纯函数 + 测试 | 小 |
| 蜡烛图渲染 | 前端手写 canvas（项目**零 CDN 依赖**是硬约束，不能用 lightweight-charts） | **中** |
| 成交量柱 | 前端（共享 x 轴） | 小 |
| 买卖点标记 | 后端暴露 fills + 前端标记 | 小~中 |
| 成交明细表 | 后端暴露 + 前端表格 + 排序导出 | 中 |
| 分析报告 | 后端算指标 + 前端卡片 + 红旗规则 | 中 |
| 测试 | 后端指标函数要有测试（项目纪律） | 中 |

**总计**：前端 `index.html` 从 1374 行预计涨到 1900~2200 行；
后端新增 2~3 个纯函数 + 若干 API 字段。**是一次中等改动，不是小修补。**

## 六、实施顺序建议（如果要做的話）

1. **先把后端数据打通**（OHLC 聚合、fills 暴露、绩效指标计算）——带测试
2. **再做主图**（K 线 + 成交量 + 买卖点）——视觉收益最大
3. **然后成交明细表**
4. **最后分析报告**（含红旗规则）
5. 每步之后重跑打包（`packaging/README.md` 的流程）并实测
