# LLM 交易 Agent + OKX 风格订单：设计方案

> 需求（用户原话）：「接入 agent 的 api，比如 agnes，然后让这个 ai 去交易、
> 去做决策、去下单，然后记录下单的理由原因，入场价格、出场价格等等的订单信息，
> 然后用于数据分析验证；然后交易的环境我希望按照真实的 OKX 交易所的情况进行下单，
> 比如杠杆啊、价格、止盈止损等等订单信息」。
>
> 本文是**先查真实 OKX 的订单模型、再查这个领域公认的评估标准、然后对项目现状**的结论。

---

## 0. 先说一件必须先定的事

**「按照真实 OKX 的情况下单」有两条完全不同的路**：

| | A. 模拟（用 OKX 的规则，不连网） | B. 真实（连 OKX 下单） |
|---|---|---|
| 撮合 | 本项目引擎，但**用 OKX 的订单语义**（杠杆/保证金/强平/TP-SL） | OKX 服务器 |
| 钱 | 无风险 | **真钱** |
| 可复现 | ✅ 完全（同种子可重放） | ❌ 不可复现 |
| 能做的事 | 所有研究、对照、留痕、评估 | 只能做"最终验证" |

**建议：先做 A**。理由不是保守，而是——
搜索到的这个领域的综述（arXiv 2605.19337）统计了 **77 篇** LLM 交易 Agent 研究，
其中只有 **19 篇**达到"有动作输出 + 闭环评估"的最低标准，而这 19 篇里
**只有 2 篇**报告了时间一致的划分协议、**各只有 1 篇**报告了明确的交易成本模型
与标的池处理，**没有任何一篇**达到可复现级别。

⇒ 这个领域当前的主要状态是「**回测表演**」。在把真钱接上之前，
先把"A 这条路"的证据链做扎实，是唯一不亏钱的做法。

**B 可以后置**：A 的订单模型如果按 OKX 语义实现，将来换成真实网关是**替换一个执行器**的事。

## 0.5 实测：Agnes 到底能不能用（3 次调用）

在写方案之前先跑了一次连通性自检（`scripts/probe_llm.py`），**结果决定了方案的形状**：

| 次数 | action | TP | SL | 延迟 |
|---|---|---|---|---|
| 1 | sell 0.15 | 102.9 | 101.8 | 2.26s |
| 2 | hold | **10350** ⚠️ | **10180** ⚠️ | 6.01s |
| 3 | hold | 103.5 | 101.95 | 1.59s |

**结论**：

✅ **可以用**：3/3 调用成功，直接给出合法 JSON，**延迟中位 2.26s**
（最慢 6.01s）⇒ 只适合「每个决策窗口一次」，不适合高频。
理由质量也不错（会提趋势、浮盈、保证金率、资金费率）。

⚠️ **但第 2 次的止盈止损量级错了 100 倍**（`10350` 而不是 `103.5`）。
如果不过校验就直接下单，TP 挂在 100 倍远的地方、SL 永远不会触发。
**这不是模型的偶发 bug，而是"LLM 不该决定数值"的实证**——
它印证了搜索里的判断：「LLM 可能擅长总结宏观，却是个糟糕的仓位引擎」。

⚠️ **三次的决策并不一致**（1 次 sell、2 次 hold，尽管 temperature=0.2）。
所以**决策稳定性本身**也要作为指标记录（同一上下文重复问，
结论是否稳定；不稳定的话，"这一次的收益"有多少是运气）。

⇒ **这两条直接决定了本方案的两条硬约束**：
1. **风控层不是可选项**：所有数值（价格、数量、杠杆）必须过**合理性校验**
   （TP/SL 必须在 mid 的合理区间内、size 不得超过上限），
   校验不过就**退回 hold 并记录原因**；
2. **同上下文要重复采样**：记录 `n_samples` 与一致性，
   不一致时按保守规则（如取多数票或不动作）。

## 1. 真实 OKX 的订单模型（查证结果）

### 下单参数（`POST /api/v5/trade/order`）

| 参数 | 取值 | 我们的现状 |
|---|---|---|
| `instId` | 如 `BTC-USDT-SWAP` | 有品种概念，需补 |
| `tdMode` | `cash` / `cross`（全仓）/ `isolated`（逐仓） | **缺** |
| `side` | `buy` / `sell` | ✅ |
| `ordType` | `market` / `limit` / `post_only` / `fok` / `ioc` | 只有 limit/market，**缺后三种** |
| `sz` / `px` | 数量 / 价格 | ✅ |
| `posSide` | `long` / `short` / `net` | **缺** |
| `reduceOnly` | 只减仓 | **缺** |
| `clOrdId` | 客户端订单 ID（≤32 字符） | 有 `order_id`，可对齐 |
| `attachAlgoOrds` | **随主单挂止盈止损** | **缺**（核心） |

### 止盈止损（`attachAlgoOrds` 里）

| 参数 | 说明 |
|---|---|
| `tpTriggerPx` / `slTriggerPx` | 触发价 |
| `tpOrdPx` / `slOrdPx` | 委托价，**`-1` 表示触发后走市价** |
| `tpTriggerPxType` / `slTriggerPxType` | 触发价取哪个：`last` / `index` / **`mark`** |
| `tpTriggerRatio` / `slTriggerRatio` | 按**比例**触发（仅 FUTURES/SWAP） |
| `attachAlgoClOrdId` | 附加单自己的 ID |

⚠️ **`mark`（标记价）这一项很重要**：真实交易所用标记价触发强平与止损，
就是为了防"最后成交价被一笔插针打穿"——这与本项目"锚点必须用同时点的真实盘口价"
那条纪律是同一种思路（别用会被单笔成交污染的价）。

### 算法单（`/api/v5/trade/order-algo`）

七种：`conditional`、`oco`（一撤一）、`trigger`、**`move_order_stop`（移动止损，
带 `callbackRatio`/`callbackSpread`/`activePx`）**、`iceberg`（冰山）、`twap`、`chase`。

### 持仓与保证金

- `GET /api/v5/account/positions` 返回：`pos`、**`avgPx`（入场均价）**、`markPx`、
  `upl`（未实现盈亏）、`imr`/`mmr`（初始/维持保证金）、`lever`
- `setLeverage(instId, lever, mgnMode)` 调杠杆
- 保证金模式：`cross` / `isolated`

## 2. LLM 交易 Agent 的评估标准（查证结果）

### ⭐ 最小证据链（六项，缺一项这个评估就是"表演"）

1. 决策时**能看到什么**信息
2. Agent **相信什么**、引用了什么
3. 建议的**动作**
4. 这个建议**是否真的变成了交易**（还是被风控拒了 / 变成观察 / 不动）
5. 什么规则**接受 / 拒绝 / 改了量**
6. 扣掉成本、滑点、风控限制后的**结果**

### 决策日志必须含

输入时间戳 · 数据来源 · **提示词模板版本** · **模型与版本** · 工具调用 ·
检索到的内容 · 建议 + **置信度** + **弃权理由** · 事后施加的风控约束 ·
最终动作与组合状态 · 在**事先声明**的时间窗上的结果

### 三层必须分开评

**预测**（估收益/波动）· **决策**（定方向/仓位/弃权）· **执行**（订单类型/时机/成本）。
「Agent 可能在一层有用、在另一层有害」——混在一起评就看不出来。

### 防"Alpha 幻觉"的四条硬控制

| 控制 | 做法 |
|---|---|
| **让泄漏难发生，而不只是禁止** | point-in-time 上下文（只取 `tick ≤ t`）+ **no-internet 回放模式**（禁外部检索，否则模型会读到答案） |
| **成本模型事先定义** | 手续费/滑点/资金费写死在配置里；**在漂亮回测之后再加成本，是边缘系统活太久的原因** |
| **弃权也要评分** | `no-op` 是决策，要记理由；好系统知道何时不交易 |
| **成本敏感性** | 报告成本 ×2、×5 后的表现 |

### 必报的量

毛收益与**净收益** · turnover · 手续费/价差/滑点假设 · 平均持仓期 ·
**交易数与「不交易」数** · 最大回撤

缺的不是"怎么评"，是"要评的那个 LLM Agent 还不存在"。

## 4. 建议架构（六层）

```
⓪ 数据层（新增，见 §4.5）——「真实 / 历史 / 自生成」三源，统一进 SQLite
   └─ 三种来源、一个 schema；按需拉取；缓存优先、联网兜底

① 数据层（Point-in-time，防泄漏的第一道）
   └─ 市场快照：盘口深度 / 近期成交 / 资金费率 / 标记价
      严格只取 tick ≤ t 的数据；上下文构造器带 hash 便于事后核对

② 决策层（LLM）
   ├─ Prompt 模板（**版本化存储**，改模板要留痕）
   ├─ 上下文构造器（把 ① 变成模型能读的文本，含"你能看到什么"的显式声明）
   └─ 输出解析器（结构化，容错解析 + 解析失败也留痕）

③ 风控层（LLM 说了不算）
   ├─ 头寸规模（按波动率与保证金，不是模型报的 sz）
   ├─ 合规检查（杠杆上限 / 单品种上限 / 回撤熔断 / 只减仓模式）
   └─ 人工否决开关（GUI 上一个按钮）

④ 执行层（OKX 语义）
   ├─ 订单模型：tdMode / posSide / reduceOnly / attachAlgoOrds / clOrdId
   ├─ 账户账本：保证金、杠杆、强平价、未实现盈亏、资金费
   └─ 撮合：复用现有引擎，外加触发单（TP/SL）的 tick 级检查

⑤ 留痕层（⭐ 需求的中心）
   └─ 每个决策一条完整记录（见下面 §5），落 JSONL，可回放
```

### 关键设计决策

- **LLM 只做"决策"，不做"算数"**：仓位、保证金、强平价全由确定性代码算。
  （搜索里明确指出：**LLM 可能擅长总结宏观、却是个糟糕的仓位引擎**。）
- **弃权是一等公民**：`no-op` 与买卖一样进留痕，且评估时要单独看弃权质量。
- **回放模式默认关外部访问**：LLM 只能看我们给的上下文——
  这是防"读到答案"的唯一可靠做法（不是靠嘱咐它别上网）。
- **每次决策都记 prompt 模板版本与模型名**：否则半年后不知道哪版的成绩。

## 4.5 数据层（2026-09-20 用户新增需求）

> 用户原话：*「实时拉取 OKX 或其他交易所数据…建立一个数据库 sqlite…
> 不必所有币种都拉，在选择准备交易的时候才去拉…也可以下载历史数据，
> 还有自己生成数据，这样子 agent 可以利用不同来源的数据进行自我测试、真实数据测试。」*

### 三种数据来源，一个 schema

| 来源 | 用途 | 获取方式 | 关键属性 |
|---|---|---|---|
| `live` | **真实盘面**（当前） | OKX 公开端点，按需拉 | 有网络依赖；**不可复现**（数据会变） |
| `history` | **真实历史**（回测） | OKX 历史端点，一次拉完存库 | 落库后**可复现**；有 3 个月/3 年上限 |
| `synthetic` | **自生成**（压力测试） | 复用本项目 ABM 引擎 | **完全可复现**；已知 ground truth |

⭐ **三者用同一张表**，只多一列 `source`。这是刻意的设计：
Agent 的**同一套策略代码**应该在三源上跑出可对比的结果；
如果三源走三套接口，那么「策略在真实数据上表现不同」到底是策略的问题
还是接口口径的问题，就分不清了——**这正是本项目「同一个量不要有两条路径」
那条纪律的同一形态**。

### SQLite 库结构（草案）

```sql
-- 行情：三源共用。source + inst_id + bar + ts 是唯一键
CREATE TABLE candles (
  source TEXT NOT NULL,          -- 'okx' | 'synthetic'
  inst_id TEXT NOT NULL,         -- 'BTC-USDT' / 'BTC-USDT-SWAP'
  bar TEXT NOT NULL,             -- '1m' '15m' '1H' '1D'
  ts INTEGER NOT NULL,           -- 毫秒（开盘时间，与 OKX 一致）
  open REAL, high REAL, low REAL, close REAL, volume REAL,
  confirm INTEGER DEFAULT 1,     -- OKX 的 confirm 字段：0=未走完
  fetched_at INTEGER,            -- 本地写入时刻（区分「数据时间」与「拿到时间」）
  PRIMARY KEY (source, inst_id, bar, ts)
);

-- 快照类（无需 OHLC 的量）：资金费率 / 未平仓量 / 标记价
CREATE TABLE metrics (
  source TEXT, inst_id TEXT, kind TEXT,   -- 'funding_rate'|'open_interest'|'mark_price'
  ts INTEGER, value REAL, extra TEXT,      -- extra 存 JSON（如 nextFundingTime）
  PRIMARY KEY (source, inst_id, kind, ts)
);

-- 盘口快照（实时拉取时选存；全存会很占空间）
CREATE TABLE books (
  source TEXT, inst_id TEXT, ts INTEGER, sz INTEGER,
  bids TEXT, asks TEXT,        -- JSON: [[px, sz, n], ...]
  PRIMARY KEY (source, inst_id, ts, sz)
);

-- ⭐ 拉取账本：回答「这份数据是什么时候、用什么参数拉下来的」
CREATE TABLE fetches (
  id INTEGER PRIMARY KEY,
  source TEXT, inst_id TEXT, bar TEXT,
  from_ts INTEGER, to_ts INTEGER, n_rows INTEGER,
  started_at INTEGER, finished_at INTEGER,
  endpoint TEXT,               -- 哪个端点（candles vs history-candles）
  ok INTEGER, error TEXT, pages INTEGER
);
```

**为什么 `fetches` 表不是多余的**：本项目最贵的一课是「结果对 ≠ 有能力知道
结果对不对」。行情库也一样——**没有拉取账本，半年后没人知道某根 K 线是
从哪个端点、什么参数拿的**，而 OKX 的 `candles`（热缓存，近 3 个月）与
`history-candles`（冷存储，上限 100 条）**可能返回不同的修正后数据**。

### 按需拉取（用户明确要求）

**不预下载全市场**。触发条件是「某标的一次即将开始的交易会话」：

```
用户/Agent 说「我要交易 BTC-USDT」
   ↓
① 查库：这个标的有多少数据？覆盖到什么时间？
   ↓ 不足
② 拉：candles 补近端 + history-candles 倒推补远端（分页）
   ↓
③ 存库（幂等 UPSERT），写 fetches 账本
   ↓
④ 会话开始了，之后全程只读库（决策路径不碰网络）
```

⭐ **第 ④ 步是硬约束，不是优化**：决策期间联网 = 引入不可复现性 +
可能读到未来数据。**库是决策路径的唯一数据源。**

### OKX 公开端点（查证结果，全部**无需鉴权**）

| 端点 | 用途 | 单次上限 | 限频 |
|---|---|---|---|
| `/api/v5/market/candles` | 近期 K 线（**近 3 个月**，热缓存） | **300** | 40 次/2s |
| `/api/v5/market/history-candles` | 历史 K 线（**主流币约 3 年**，冷存储） | **100** | 20 次/2s |
| `/api/v5/market/books` | 盘口深度 | `sz` 5/10/20/50/100/400 档 | — |
| `/api/v5/market/trades` | 最近成交 | — | — |
| `/api/v5/public/funding-rate` | 资金费率（**仅永续**） | — | 20 次/2s |
| `/api/v5/public/open-interest` | 未平仓量 | — | 20 次/2s |
| `/api/v5/public/mark-price` | **标记价**（强平计算基准） | — | — |
| `/api/v5/public/instruments` | 合约规格（tick/lot/最小下单） | — | 10 次/2s |

⚠️ **两个坑（查证时发现，不踩第二次）**：

1. **分页参数命名反直觉**：`after` 传时间戳返回的是**比它更早**的数据、
   `before` 返回**更新**的。倒推历史要用 `after` 翻页，且两者**不能同时传**。
   翻页时取上批最旧一条 `ts − 1ms` 作为下一次 `after`——
   **减 1ms 是必须的**，否则边界那根会出现在两批里（重复写入会被主键挡掉，
   但会污染 `n_rows` 统计）。
2. **`confirm` 字段**：`'0'` 表示这根 K 线还没走完、价格仍在跳。
   **决策时必须只用 `confirm='1'` 的根**，否则就是读未来的数据
   （与项目「路径覆盖事件全程但不越界」同源）。

### 自生成数据（用户明确要求「自己生成数据」）

**这是本项目最有优势的一块——引擎已经在那儿了。**

价值不在于「造更多数据」，而在于造**已知 ground truth 的对照**：

| 生成方式 | 能验证什么 | 为什么真实数据做不到 |
|---|---|---|
| 改 `scenarios.py` 参数 | 策略在极端行情下的行为 | 真实数据里很少出现 liquidation 场景 |
| 注入已知冲击 | Agent 能否识别并正确反应 | 真实市场的事件归因本身有内生性问题 |
| **同种子重跑** | Agent 决策的可复现性 | 真实数据只有一条路径，无法重放 |
| 调主体构成（零智能/基本面/图表派比例） | 策略对市场微结构的敏感性 | 无法控制真实市场的主体构成 |

⭐ **最关键的一条**：自生成数据能让「**Agent 的收益是本事还是行情**」这个问题
有一个**答案已知的对照组**——因为我们可以造出「基本面随机游走、
完全没有可预测性」的市场，此时任何正收益都只能是运气。
**这类对照在真实数据上永远做不了。**

### 与测量纪律的接口

- **`live` 数据进库后就不再更新**（同一 `(source,inst,bar,ts)` 不覆盖）
  → 保证「当时的决策」事后可复现，哪怕交易所之后修正了历史
- 每条决策留痕里记 `data_snapshot_id`（库里数据的最大 ts + 拉取时间）
  → 半年后能确认「那次决策看到的是哪一版数据」
- **`synthetic` 源必须记构造参数**（种子 + 场景名），否则无法重造

## 5. 决策留痕的结构（需求的中心）

一条记录 = 一次决策的完整因果链：

```jsonc
{
  "decision_id": "sha256(tick|role|params|time)",   // 确定性 ID，可复现
  "run_id": "…", "tick": 3120, "wall_ms": 1758...,
  "context_hash": "…",            // 当时可见数据的哈希（防事后篡改）
  "prompt_template": "v1.2",      // ⭐ 模板版本
  "model": "agnes-2.5-flash", "model_params": {"temperature": 0.2},
  "visible_state": {              // ⭐「决策时能看到什么」
    "mid": 102.44, "spread_bp": 8.1, "mark": 102.5,
    "depth_bid": [...], "depth_ask": [...],
    "funding_rate": 0.0001, "inventory": 0.3, "margin_ratio": 0.42,
    "recent_closes": [...]
  },
  "llm_raw": "……模型原始输出，不截断",     // 解析失败也要留
  "parsed": {                              // 建议 + 置信度 + 理由
    "action": "buy", "sz": 0.5, "px": null, "ordType": "limit",
    "tp": 103.5, "sl": 101.2, "confidence": 0.72,
    "reason": "……自然语言理由（用户明确要求记录的）"
  },
  "risk": {                                // ⭐ 什么规则改/拒了它
    "accepted": true, "resized_to": 0.35, "rule": "vol_target",
    "notes": ["杠杆 3x ≤ 上限 5x", "单品种敞口 12% ≤ 20%"]
  },
  "order": {                               // ⭐ 最终落成的订单（OKX 语义）
    "tdMode": "isolated", "posSide": "long", "reduceOnly": false,
    "attachAlgoOrds": [{"tpTriggerPx": 103.5, "tpOrdPx": -1,
                        "slTriggerPx": 101.2, "slOrdPx": -1,
                        "tpTriggerPxType": "mark", "slTriggerPxType": "mark"}],
    "clOrdId": "tw-3120-01"
  },
  "outcome": { ... }   // 事后回填：成交价、滑点、h 后 markout、平仓盈亏
}
```

**「入场价 / 出场价」在 OKX 语义下不是订单上的字段，而是持仓账本的产物**：
- 入场价 = 该持仓的 `avgPx`
- 出场价 = 平仓成交价
⇒ 所以记录要**关联到持仓**，而不是只看单笔订单。

## 6. 评估体系（分层，且必须与基准对照）

| 层 | 指标 | 对照 |
|---|---|---|
| **决策层** | 弃权率、置信度校准（说 0.7 的是不是真 70% 对）、理由可用性 | — |
| **执行层** | 实际滑点 vs 预期、成交率、下单延迟 | — |
| **结果层（毛）** | 收益、Sharpe、最大回撤 | — |
| **结果层（净）** | **扣手续费+滑点+资金费**后的收益 | ⭐ **与 `noop` 对照** |
| **成本敏感性** | 成本 ×2 / ×5 后还活着吗 | — |
| **稳健性** | 跨 5 个场景 × 多种子 | 同种子配对 |

⭐ **最关键的一条**：**LLM 必须显著优于 `noop`（什么都不做）**。
项目里 `noop` 的 PnL 恰好是 0，`random_taker` 是稳定亏损——
这两条基准线**已经现成**。如果 Agent 打不过 noop，
那它做的所有"分析"都只是在给自己找理由交易。

## 6.5 MCP 服务（2026-09-20 用户新增需求）

> 用户原话：*「还有也要做 MCP，方便 agent 调用」*

### 先分清「谁的 Agent」

这一节有个容易混的地方，必须写清楚：

| 场景 | 谁是 MCP 的「客户端」 | 什么在调工具 |
|---|---|---|
| **本项目的 LLM 交易 Agent** | 项目自己 | ❌ **不需要 MCP**——项目直接 import `tw/*` 更快更可控 |
| **外部 Agent**（Claude Desktop / Cursor / 其他） | 那些宿主 | ✅ **需要 MCP** |

⇒ **MCP 的价值是「让外部 Agent 能操作这个项目」**，不是给内部 Agent 用。
内部 Agent 走 Python 函数调用；MCP 是**对外的一扇门**。

### 三种消费者（各自的用法不同）

1. **外部 AI 助手**（Claude/Cursor）→ 让它帮你查行情、看实验、跑对照
2. **本项目自己的开发**（我）→ 用 MCP 校验接口设计是否自洽
3. **未来的多 Agent 协作**（§7 的 C 路线）→ Agent 之间通过 MCP 共享能力

### 工具设计（按「读写分离 + 危险度分级」）

⚠️ 关键安全原则：**能读的和能下单的不能是同一批工具**，
且**能下单的工具默认不启用**。

**只读类（默认启用，无副作用）**

| 工具 | 参数 | 返回 |
|---|---|---|
| `list_instruments` | `source`（okx/synthetic） | 库里有数据的标的 + 时间范围 |
| `get_candles` | `inst_id, bar, from_ts, to_ts, limit` | OHLCV 数组（**列式**，省 token） |
| `get_market_snapshot` | `inst_id` | 当前 bid/ask/mid/spread/资金费率/标记价 |
| `list_scenarios` | — | 5 个场景名 + 描述 |
| `list_strategies` | — | 可用策略名 |
| `get_run_summary` | `run_id` | 该次实验的指标汇总 |
| `get_decision_log` | `run_id, limit` | 决策留痕（含理由、入场出场价） |
| `compare_runs` | `run_id_a, run_id_b` | 两两对照 + **区间重叠判定**（复用第十条纪律） |

**写入类（需显式开启）**

| 工具 | 说明 | 护栏 |
|---|---|---|
| `fetch_data` | 按需拉 OKX 数据入库 | 只允许白名单 `inst_id`；限频；写 `fetches` 账本 |
| `run_backtest` | 跑一次实验 | 上限 tick 数（复用 `MAX_LAB_TICKS` 思路） |

**交易类（⭐ 默认关闭，`TW_MCP_ALLOW_TRADE=1` 才启）**

| 工具 | 说明 |
|---|---|
| `place_order` | 下单（A 路线 = 写进模拟账本；B 路线 = 真钱） |
| `cancel_order` / `get_positions` | — |

⚠️ **A 路线（模拟）下这些工具安全**（只改内存账本）；
**B 路线（真钱）下必须**：独立进程 + 独立 token + 单笔上限 + 日累计上限 +
人工确认开关。**在做 B 之前，这一组不放出去。**

### 技术选型（查证结果 + **实测修正**）

- **官方 Python SDK 已到 v2**（`mcp` **2.2.0**）；v2 是大重写，v1.x 仍在维护。
  **新项目直接用 v2。**
- ⚠️ **v2 把 `FastMCP` 改名成了 `MCPServer`**（`from mcp.server.mcpserver import
  MCPServer`）。网上绝大多数教程仍是 v1 的 `from mcp.server.fastmcp import FastMCP`，
  **照抄会在 v2 上直接 `ModuleNotFoundError`** —— 本轮实测踩到。
  实现里 `_require_mcp()` 兼容两者，优先 v2。
- ⚠️ v2 字段风格从 camelCase 转到 snake_case：`serverInfo`→`server_info`、
  `inputSchema`→`input_schema`、`structuredContent`→`structured_content`、
  `isError`→`is_error`。实测协商到的协议版本是 **2025-11-25**。
- **`@tool()` 装饰器风格不变**：函数签名 + docstring 自动变成 JSON Schema，
  **零样板代码** —— 这一点 v1/v2 一致。
- **transport 选 `stdio`**：客户端把服务作为子进程拉起，走 stdin/stdout 的
  JSON-RPC。**不绑端口、不需要 TLS、单机默认安全**——与本项目 GUI 那套
  「只绑 127.0.0.1」是同一个安全哲学
- 备选 `streamable-http`：仅当要跨机时用（未来多 VM 场景）
- ⚠️ **`python -m 包名` 需要 `__main__.py`**：光有 `__init__.py` 里的
  `if __name__ == "__main__"` 不会执行。与打包那次「入口与包同名」是同一类问题
  （运行方式与文件结构不匹配）。

**教训**：只读文档不试跑，会在「类名」这种最表层的地方翻车。
**写 MCP 服务前先 `pip install` 再 `import` 一次，比读十篇教程有用。**

### ⚠️ 一条必须提前说的依赖风险

**`mcp` 是第三方包，而本项目现在的依赖只有 numpy / scipy / matplotlib**
（`tw/realdata.py` 的注释里明确写过「多一个 pandas 就多一个『环境不对所以
没跑』的借口」）。

⇒ 处理方式：
1. **MCP 服务作为可选组件**，放在 `mcp_server/` 目录，**不进核心测试链**
2. `import mcp` 失败时**给出明确指引**（`pip install "mcp>=2.2.0"`），不静默
3. 核心库 `tw/*` **绝不 import mcp**——保证「不装 mcp 也能跑全部研究」
4. 在 `packaging/` 的 exe 里**默认不打进去**（体积 + 用不上）

### 目录结构（建议）

```
mcp_server/
├── __init__.py
├── server.py        # FastMCP 实例 + 工具注册
├── tools_read.py    # 只读工具（行情/实验/留痕）
├── tools_write.py   # 写入工具（拉数据/跑实验）
├── tools_trade.py   # 交易工具（默认关闭）
└── README.md        # 如何挂到 Claude Desktop / Cursor
```

**验收方式**：用 `mcp dev server.py`（MCP Inspector）逐个调通工具，
并**用一个真实外部客户端连一次**——自己写的客户端测不出兼容性问题。

### 交付

|---|---|---|---|
| A1 | `tw/order_model.py` | 419 | `tests/test_order_model.py` |

| A2 | `tw/decision_log.py` | ~520 | `tests/test_decision_log.py` |
| A2 | `tw/risk.py` | ~430 | 同上 |

**A1/A2 合计 100 + 102 = 202 项新测试**；全量 **1073 项全绿**。
`tw/market.py`、`tw/types.py`、`tw/engine.py` **一个字没改**——
A1/A2 全部是新模块，因此它们的全部行为可独立验证。

### ⭐ 施工中发现并修正的真实缺陷（六个）

这一节比"交付了什么"更重要：**下面每一条都是先写错了、被测试抓住的**。

**① 保证金率的口径会让"下跌"看起来像"变安全"**（A1）

`(权益 − 维持保证金) / 名义价值` 这个口径下，价格下跌时**分子分母同时缩小**，
而分母缩得更快 ⇒ **ratio 反而变大**。

实测：持仓 1 BTC @100、cash=10 时，mark=110 得 ratio≈9.996，
mark=95 得 ratio≈90.996。也就是说 `ratio 上升 ≠ 安全`。

- **处置**：不改公式（它是对的，只是**方向约定**与"比率越大越安全"相反），
  而是①在 `MarginAccount.margin_ratio` 的 docstring 里加 `⚠️⚠️` 段；
  ②测试改名为 `test_保证金率口径是越小越危险`；
  ③新增 `test_保证金率在强平价处趋近零`，把 `margin_ratio` 与
  `is_liquidated` **两个口径接起来**——单看任一个都可能理解反。
- **为什么值得记**：这是"两个都对的东西放在一起会被读错"的典型。
  真实交易系统里保证**一个**口径贯穿全部界面，比公式本身更重要的。

**② 强平价公式的分母多空不同**（A1）

多头 `(avg·q − cash) / (q(1−m))`，空头 `(avg·q + cash) / (q(1+m))`。
抄成一个分母会让空头强平价被算低 ⇒ **该强平时看起来还安全**。

- **处置**：加了 `M68` 变异体专门注入这个错误；
  代码里在空头分支写了 "与多头不同，别抄错" 的注释。

**③ 风控的步骤顺序让 `size_cap` 成了不可达代码**（A2，**最隐蔽的一个**）

原实现里「量上限裁剪」排在「敞口检查」**之后**。后果：

```
Agent 说"买 1000"，账户 10,000
→ 敞口 = (0 + 1000×100)/10000 = 1000% > 60%  ⇒ 判 exposure_cap **拒单**
→ size_cap 那条裁剪分支**永远走不到**
```

它不报错、不警告，只是那条分支再也不会执行。**这四条测试一开始全是红的**，
而失败信息（`accepted` 是 False）看起来像"断言写错了"。

- **处置**：把裁量步提到敞口/保证金**之前**——裁剪后的量才是敞口与保证金
  应当使用的输入。用**裁剪前的量**去算它们，等于拿一个不会发生的订单
  去拒绝一个会发生的订单。
- **配套**：`equity <= 0` 时 `cap` 必须显式清零。原来 `if equity > 0` 才取
  `min`，导致 `equity=0` 时 `cap` 停在 `max_notional=20000`
  ⇒ **一个 0 本金的账户能开仓**，账户层不变量 `equity >= 0` 被绕过。
- **配套 2**：拒单时必须清空 `resized_to`。留着它会让下游把它算进
  `resized_frac` 并在 `summary_line` 里打印 `[改量→30]`——**实际一手都没成交**。
  这是"字段语义被两种含义混用"的典型：静默、且难以发现。
- **回归守卫**：加了 4 条测试专门锁这个顺序（含一条从风控层接到留痕层
  `log_stats` 的，验证 `resized_frac=0` 且 `rejected_frac=1`）。

**④ `cash=0` 时强平价会落在开仓价上方**（A1，**不是 bug，是我的断言假设错了**）

`liq_price` 在 `cash=0` 时给出 101.01 > avg 100（多头）。一开始判定为公式错。
复核后：`cash=0` 意味着**用 0 本金开 200 名义值的仓**，不可物理；
此时"权益 = 维持保证金"的解确实落在 avg 上方。

- **处置**：测试改用 `cash=50`（liq=75.7576），并**代回验证
  `equity(liq) == mm(liq)`**（这才是强平价的定义，比背公式可靠）；
  在 docstring 里写明「后来者很容易用 `cash=0` 重写这条测试，
  然后得出『公式错了』的错误结论」。
- **为什么值得记**：这是"测试写错了但看起来像代码错了"。
  区分方法是——**回到定义去验**，而不是比对期望值。

**⑤ `**extra` 把「签名上堵住泄漏」的设计整个架空了**（A2，**收尾时才发现的**）

`build_visible_state` 的签名上**确实没有** `future_*` 参数——这一点在
README 里被当成"从签名上堵住答案泄漏，而不是靠纪律"的优点写着。
但函数还有 `**extra: Any`，而它是个**不受限入口**：

```python
st = build_visible_state(mid=100.0, fundamental=100.0,
                         future_close=999.0, outcome_pnl=12345.0)
# → {'mid': 100.0, ..., 'future_close': 999.0, 'outcome_pnl': 12345.0}
```

实测确认**泄漏字段真的进了 ① 可见状态**。危险之处在于它**完全静默**：
签名上"没有 `future_*` 参数"的承诺仍然成立、看上去依然对，
守卫被绕过的表现是零——`tests/test_decision_log.py` 里那条
`test_不接受未来数据参数`（遍历 `sig.parameters` 查前缀）**照样全绿**。

- **处置**：保留 `extra`（自定义字段确实有用途），但**守卫键名**——
  新增 `_is_leaky_key()`，以 `future` / `outcome` / `lookahead` /
  `hindsight` 开头且在**词边界**上结束的键一律 `ValueError`。
- ⚠️ **词边界不能省**：第一版守卫用朴素的 `startswith`，
  结果 `futures_basis`（期货基差——这是决策当时**真的能看到**的数据）
  被误杀。**一个误杀过多的守卫，最后会被人整体关掉**，
  于是保护归零。判据是前缀后一个字符不是字母（下划线/数字/结尾都算边界）。
  这条是**被我自己写的测试抓出来的**（`test_泄漏键判定是纯函数` 一开始是红的）。
- **配套**：4 条新测试 + `M77` 变异体。M77 拆除守卫后首挂正是
  `test_extra不能挂未来字段` / `test_extra不能挂事后结果` /
  `test_extra大小写与空白也拦`。
- **可复用的判据**：**凡是"靠签名结构来保证"的设计，都要检查是否有
  `**kwargs` 类的逃生口**。有逃生口，签名就不是约束，只是文档。

**⑥ 一个"活着"的变异体：M63 靠乘性噪声伪造了影线**（数据层，**上轮遗留**）

全量 76 个变异体跑完时发现 **M63 仍全绿**（唯一一个漏网的）。
M63 把合成 K 线的
`hi = max(hi, p0, p1) * (1.0 + abs(rng.normal(0.0, 2e-4)))`
改成 `hi = max(p0, p1)`——听起来"K 线退化成折线"。

**但已有的 `test_必须有影线` 抓不住它**，原因是 M63 修改的是**两行里的第二行**，
第一行的路径极值 `hi = max(hi, p0, p1)` 还在。而第二行那个
`* (1 + 噪声)` 是**乘性**的，它自己就会让 `high > max(o,c)` 成立：
实测 **49/49 根仍然"有影线"**。测试问的是"有没有影线"，
而真正被破坏的性质是"**影线有多真**"——影线从路径极值（~1e-3 量级）
退化成噪声地板（~2e-4 量级）。

- **处置**：新增 `test_影线不是靠乘性噪声凑出来的`，
  判据是"**有相当比例的根，影线显著大于噪声地板**"——
  实测真实代码 8 个种子稳定在 **90~110 / 199**（≈45~55%），
  阈值取 20%；注入 M63 后是 **0 / 199**，判然分明。
- ⚠️ 第一版我还写了个"上影线中位数 < 5e-4"的辅助断言，
  **实测本身就不成立**（真实中位数 1.07e-3，且随种子漂移）——
  辅助判据不如单一决定性判据可靠，已删掉。
- **可复用的判据**：**"存在断言"≠"有分辨力"**。
  一条弱测试（"有没有影线"）与一条强测试（"影线是不是真的"）
  在通过时长得一模一样——**只有在变异体下才分得开**。
  这正是"这套测试能不能失败"必须全量跑、而不能只抽样跑的原因：
  抽样会漏掉唯一那个漏网的。

### 变异验证

新增 **14 个变异体**（`M64~M71` 订单模型与账户、`M72~M77` 留痕与风控），
全部用 `--only` 单独跑过，确认**真能变红**。
**全量 77 个变异体已跑完整轮，检出率 77/77**（含补强 M63 之后）：

| 编号 | 注入的错误 | 为什么它值得被守住 |
|---|---|---|
| M64 | 空头止盈触发方向不取反 | 把止盈做成**立即触发的止损**，比没有更糟 |
| M65 | 市价单用 1e18 而非 ±inf | 该成交的单永不成交，**连报错都没有** |
| M66 | post_only 交叉判定反向 | 名义 maker 实付 taker（费差 2.5 倍），仍按 post_only 记账 |
| M67 | reduce_only 超量不裁剪 | 平仓单能平出反向仓位 |
| M68 | 多空强平价共用一个分母 | 空头该强平时看起来安全 |
| M69 | 缺标记价的仓位按 0 估值 | ≤"缺失值当 0"，研究代码最常见的偏差源 |
| M70 | 强平判据用 `<` 而非 `<=` | 恰好踩线不被强平，而那是数值上最常见的位置 |

| M76 | decision_id 不含 prompt 版本 | A/B 换 prompt 的两个实验算出同一个 ID，归因失效 |
| M77 | 去掉 `visible_state` 的 `**extra` 键名守卫 | ① 可见状态能被塞进 `future_close`，回放读到未来数据；**且完全静默** |

### ⚠️ 变异体本身也会写错（M71 第一次是"恒等变换"）

M71 第一版注入的是 `eq_after = self.cash + self.total_upl(marks)`
（即删掉 `- p.upl(m) + upl`），**跑出来仍全绿**。

复核后发现：`total_upl` 的定义就是**对所有仓位求和 `p.upl(m)`，
其中包含 `p` 本身**。所以 `- p.upl(m) + upl` 恰好是"把 p 的 upl
换成模拟后的 upl"，而删掉它——当 `p` 是空仓时，`upl` 本来就等于
`p.upl(m)`，**这是一个恒等变换**。

- 判定：**不是测试漏了，是变异体没注入任何东西**。
  这与"永远变红的变异体"是同一种病：**没有信息量**。
- 修法：改成 `eq_after = self.cash + self.total_upl(marks) - p.upl(m)`
  （= 新仓带来的盈亏当成 0），这才真的改变了行为。
- **配套补测试**：新增 `test_在亏损仓位上继续加仓要看加仓后的权益`
  与 `test_加仓后的模拟权益必须等于真实重算值`
  （后者把 `can_open` 的**模拟路径**与"真成交后重算"的**真实路径**
  在同三个终态上对拍——比断言一个期望值更可靠）。
- **可复用的判据**：写变异体后要问一句
  **「把这一行删掉/改掉，是否存在任何输入让它产生不同的输出？」**
  如果不能举例，那它就不是变异体，是注释。

### 真机 A/B 实测（BTC/ETH 永续 1H，各 8 次决策 × 3 采样）

这是 A3 最实质的产出——**同一个模型、同一份行情，只换 prompt 模板版本**：

| | v1 BTC | v1 ETH | v2 BTC | v2 ETH |
|---|---|---|---|---|
| 解析成功率 | 100% | 100% | 100% | 100% |
| **成交比例** | **12.5%** | **37.5%** | **50.0%** | **75.0%** |
| 主动弃权 | 87.5% | 62.5% | 37.5% | 25.0% |
| 被风控拒 | 0% | 12.5% | 12.5% | 0% |
| 延迟中位 | 8.6s | 8.5s | 9.3s | 8.3s |

**结论**：v2 把成交率提高了 **约 3~5 倍**，而**唯一改动是提示词的形状**
（把"数据源不提供的字段"折叠成一行 + 明确告诉它"你能用收盘价推断什么"）。
⇒ 这直接证明了一件事：**在 LLM 交易里，"告诉它你有什么"比"给它更多数据"更关键**；
而"Agent 很保守"这个观察，很可能只是提示词没把可用信息讲清楚。

⚠️ **但必须同时说清楚三条边界**：

1. **样本极小**（每格 8 次决策），差距虽大但**不足以下统计结论**。
   按本项目测量纪律，这类比较要走**区间重叠检验**才算数——留给 A4。
2. **v2 的高成交率不等于高收益**。它只是"更愿意动手"。
   收益要等 A4 的分层评估（与 `noop` / `random_taker` 对照）才有答案。
3. **本会话未更新账户状态**（`run_session` 的 `on_record` 钩子没用上），
   所以每次都看到"空仓 / equity 不变"。这**不影响管线验证**，
   但它意味着**当前数字不能当作策略收益**——A4 必须先接上账户。

### ⭐ 施工中发现的真实缺陷（四个，全部是静默型）

这一轮的价值几乎全在这里：**它们都不报错、日志看起来正常**。

**① 回放把 N 次采样压成 1 次（覆盖式索引）——最严重的一个**

`ReplayClient` 第一版索引写成 `dict[prompt_hash] = 记录`。
但多采样时**同一 prompt 会调用 N 次**，每次录一条 ⇒ 后写的把先写的**覆盖**。

后果（实测数字）：
```
真机：tick 113 三次采样 = [hold, hold, buy] ⇒ 多数派 hold
回放：三次都返回最后那条 "buy"        ⇒ 多数派 buy   ← 方向整个反过来
```
而**覆盖率仍显示 100%、零报错**。这个 bug 活过了第一轮验证，
是靠**逐条比对 live/replay**（而不是看汇总数字）才发现的。

- **修法**：索引改成 `prompt_hash → 响应列表`，按调用次序依次发出；
  条数不够就报错（静默少发一条会让"这次有几个样本"消失）。
- **回归守卫**：`test_多采样整个回合可复现` —— 覆盖式索引下必红。
- **可复用判据**：**"覆盖率 100%"只说明"找到了"，不说明"找对了"。**
  摘要级指标（覆盖率、成功率）无法发现"取错了哪一条"这类错误；
  唯一有效的手段是**逐条比对**。

**② `decision_id` 跨会话永远对不上（run_id 带墙钟时间）**

CLI 原来写 `run_id=f"cli-{int(time.time())}"`。而 `decision_id` 含 `run_id`
⇒ 同一份数据、同一份 prompt 在两次运行里算出**不同的 ID** ⇒
「回放能不能核对上」这件事**从构造上就不可能成功**——
而它恰恰是回放存在的唯一理由（§5）。

- **修法**：`run_id` 改为**按参数派生**（标的天数/模板/采样数/权益/区间），
  不含时刻。要看时间的话留痕里有 `wall_ms`，不必挤进 ID。
- **可复用判据**：**确定性 ID 里不许有任何"这次运行的时刻"。**

**③ `parse_ok` 判据错，导致"失败但没说为什么"的记录**

原判据是「**第一次**采样有没有解析成功」（`parsed_list[0]`）。
实测：3 次采样里第 1 次失败、后 2 次成功并选出了多数派，
却被记成 `parse_ok=False`，而且 `parse_error` 是**空串**。

改成看最终 `parsed` 里的 action 后，又踩了第二个坑：
`majority_sample` 在**全部失败**时会**造一条 hold 兜底**，
那条兜底的 action 也是 `"hold"` ⇒ **"全失败"被读成"解析成功"**。
（造一个看起来合法的兜底值 = 把故障伪装成正常，本项目最警惕的形态。）

- **修法**：判据 = `n_ok > 0`，且必须**看采样列表，不看最终 `parsed`**；
  全失败时 `parsed` 保持**空 dict**（诚实的状态）；
  部分失败时 `parse_ok=True` 但 `parse_error` 写明"3 次中 1 次无有效结果"。
- **回归守卫**：`test_全部采样失败才算解析失败` / `test_解析失败必有说明`。

**④ 四舍五入被算成"风控干预"，污染 `resized_frac`**

提示词里的"建议最大量"原来有 **17 位有效数字**（`0.24730285325666945`），
模型照抄时写 6 位小数 `0.247303` ⇒ 比上限大 1e-5 的相对量 ⇒ 触发 `size_cap`。

而 `resized_frac` 是**用来量化"风控贡献了多少"的**（A4 要报）。
把纯四舍五入算成风控干预 = **给风控记一笔假功劳**。

- **修法（两处）**：
  ① 建议量**向下取整到 2 位有效数字**（`0.24`），从一开始就不邀请这个错误；
  ② `RiskDecision` 加 `resize_is_material` 字段，按**相对幅度**（阈值 `1e-4`）
     区分"实质裁剪"与"噪声"；`log_stats` 的 `resized_frac` 只数实质的，
     另给一个 `resized_any_frac` 数全部。
- **关键区分**：**正确性与归因是两件事**。量**确实**被夹了（正确性不能让步），
  但这次不算风控的功劳（归因要准）。两个事实都要留。
- **回归守卫**：`test_建议量永不超上限`（跨 36 组量级）/ `test_统计区分噪声与干预`。

### 另外两条观察（不是缺陷，但重要）

**⑤ 模型会引用快照里根本没有的外部信息（幻觉实证）**

v1/BTC 的某一根决策理由写着：

> 「…且**标普期货与恒指期货均上涨**提供共振支撑」

而 `visible_state` 里**没有**任何外部市场数据，prompt 也明确写了
"不要引用任何未在快照中出现的信息"。

⇒ 这是设计文档 §4「回放模式默认关外部访问」那条设计的**实测反面证据**：
**你无法用提示词阻止模型使用训练知识**。它不会"上网检索"，
但它会**记得**。所以"关掉外部访问"只能约束工具调用，不能约束记忆——
评估时必须把这一条计入"Agent 的决策依据**不可完全审计**"这个已知边界。
（A4 可加一个"理由里提到的实体是否在可见状态中"的自动扫描。）

**⑥ 数据源缺字段会直接改变 Agent 的行为**

v1 的弃权理由高频出现「资金费率为 0」「买卖盘缺失」——
模型把注意力花在了**真实 OHLCV 库里本来就没有的东西**上，
于是"缺什么"压倒了"有什么"。这正是 v2 那两处改动的由来。

⇒ 可复用结论：**给 LLM 看的数据，"缺了什么"要和"有什么"一样被显式管理。**

### 变异验证（A3）

新增 **7 个（M78~M84）**，目标全是"**静默失效**"——
不报错、结果看起来正常、只有逐条核对或变异测试才分得出来：

| 编号 | 注入的错误 | 为什么它危险（都是实测踩过的） |
|---|---|---|
| M78 | 缺 key 时静默返回 hold | 跑起来完全正常，只是**永远不交易**——假装成"Agent 很保守" |
| M79 | 解析层"帮模型改量级"（10350→103.5） | 抹掉"模型数值不可靠"这个最该被量化的事实 |
| M80 | 回放按 prompt 只存最后一条响应 | 多采样多数派**方向整个反过来**，覆盖率仍 100% |
| M81 | 可见状态用"序列末尾 N 根" | i 在中间时取到**未来**的根，不报错，只让那天"神奇地准" |
| M82 | mid 取 (high+low)/2 | high/low 是事后极值 ⟹ 同一根 K 线内的泄漏 |
| M83 | 全失败时用兜底 hold 当解析成功 | 把"全部解析失败"伪装成"解析成功" |
| M84 | 建议最大量用全精度 | 模型取整后超限 ⟹ `resized_frac` 被四舍五入污染 |

这正是「回放能验证管线没有隐藏状态」那句话的实测支撑。

### ⭐ 用户点名要的那条基线：为什么它比 noop 更重要

设计方案 §6 只说「LLM 必须显著优于 `noop`」。但**只跟 noop 比是不够的**：

> 如果 Agent 赢了，赢的是**模型**，还是**可见状态里的信息**？

`visible_state` 里有最近 12 根收盘价——那是一份**有信息量的**输入。
任何一个照着它写十条的规则都可能赚钱。所以"赢了 noop"只证明
"这个状态有信息"，**不证明模型有用**。

⇒ 因此新增 `tw/policy.py`：它们吃**完全一样**的 `visible_state`、
走**完全一样**的风控与执行路径，唯一差别是"决策由谁做"。
**只有当 LLM 明显赢过这些规则，才谈得上"模型有贡献"。**

这是用户提出这条基线时点到的要害，也是本轮设计上最重要的一处补充。

### ⭐ 执行模拟的四个假设（**这是结论的一部分，不是实现细节**）

我们只有 OHLCV——**没有逐笔、没有盘口、没有排队位置**。
用四个数还原"这一小时怎么走"必然丢信息。本模块的立场是
**宁可系统性偏悲观**（偏乐观的回测会让人以为能上线）。

| # | 假设 | 偏向 |
|---|---|---|
| 1 | 市价单在**次根开盘价** ± 滑点成交 | 中性 |
| 2 | 限价单只要 `low ≤ px ≤ high` 就算成交 | ⚠️ **偏乐观**（无排队位置） |
| 3 | 当根内 TP 与 SL **同时**落在区间 ⇒ **按 SL 处理** | ✅ **偏悲观**（我们主动选的） |
| 4 | 标记价用当根**收盘价**近似 | 中性偏乐观 |

**假设 3 值得单独说**：真实世界里 TP/SL 谁先到取决于当根的**价格路径**，
而我们只看到一个区间。任何"选一个"都是在补路径——**选 TP 让回测变好看，
选 SL 让它变难看**。A1 的 `AlgoOrder.triggers` 回答不了这个问题
（它问"给定一个已知价格触发了吗"），因为这是**严格更难的问题**。
本模块显式选 SL，并把这个选择记进 `Fill.reason`，可被审计。

### 施工中发现并修正的真实缺陷（两个）

**① `ExecConfig.cost_multiplier` 只影响滑点、完全不影响手续费**

执行器把手续费交给账本算，而账本用的是 ``MarginConfig`` 的费率——
于是 ``cost_multiplier`` 对着手续费那一半**根本没接上**。后果：

```
成本 ×5 后净收益几乎没变 ⇒ 看起来像「策略对成本不敏感」
```

一个漂亮且**错误**的结论。它之所以被查出来，是因为内部有两个
口径在互相校验（一阶近似 vs 重跑），**数字对不上**才顺藤摸到根因。

- **修法**：`MarginAccount.apply_fill` / `liquidate` 增加 ``fee_override``
  参数，由执行器显式传入 `ExecConfig` 算出的费用。
- ⚠️ 强平那一处**也要改**：漏掉它会让"成本 ×5 后"偏乐观，
  而症状**只在发生强平的样本上出现**——那种偏差最难发现。
- **回归守卫**：`test_成本倍数真的影响手续费`（要求手续费比值恰好 = 倍数）
  + 变异体 M88。

**② 与 `noop` 的对照用错了检验，导致最关键的问题答不出来**

最初一律走区间重叠检验。但 `noop` 的收益恒为 0 ⇒ 它的区间宽度是 0
⇒ 重叠比例的分母没有意义 ⇒ 输出「**无法判定（输入退化）**」。
而"能不能打赢 noop"**恰恰是 A4 最核心的那个问题**。

- **修法**：按基线是否有方差分两种检验（这正是本项目纪律 8 说的
  「单家族自己的方向判定」与「家族之间的比较判定」是两件事）：

  | 基线 | 检验 |
  |---|---|
  | **零方差**（`noop`） | **CI 是否排除基准值** |
  | 有方差 | **区间重叠** |

- **回归守卫**：`test_相对noop用CI排除检验` + 变异体 M90。

### 成本敏感性为什么必须"重跑"而不是"外推"

成本变了，策略**可能就会改变行为**。实测确实发生了：
`meanrevert` 在成本 ×5 时交易笔数从 43 掉到 41。

⇒ 本项目因此提供**两个版本**并**同时报**：
- `cost_sensitivity_rerun`（**正式结论**）：用同一批已录制的决策换成本重跑。
- `cost_sensitivity_analytic`（仅供参考）：旧收益减一个数。
  **两者的差值本身就是信息**：差得越多 ⇒ 行为对成本越敏感。

### ⚠️⚠️ 但"回放"救不了 LLM 的成本敏感性（本轮最重要的方法论修正）

一开始的想法很自然：**LLM 的决策已经录下来了，换成本回放一遍即可，
零额外 API 成本**。**这个想法是错的**，而且错得很隐蔽。

原因：**LLM 的 prompt 里含账户状态**（持仓、权益、保证金率），
而账户状态取决于成交、成交取决于成本 ⇒ 换了成本，路径**立刻发散**，
后续每一步的 prompt 都与录制时不同 ⇒ 回放未命中 ⇒ Agent 全部弃权。

实测（BTC，120 根，3 采样）：

| 成本倍数 | 回放覆盖率 | 成交笔数 | 账面净收益 |
|---|---|---|---|
| ×1 | **100.0%**（360/360，逐笔复现真机） | 27 | −33.29 |
| ×2 | **0.8%**（363 次调用只命中 3 次） | **2** | −444.47 |

**那个 −444 看起来像一个成本敏感性结果**（"成本翻倍后亏损扩大 13 倍"），
**其实是回放失败**——Agent 之所以不交易，是因为我们没给它对应的 prompt。

⇒ 两条处置：
1. `cost_sensitivity_rerun` **检查回放覆盖率**，低于 95% 时该档
   **不出数字**，只标 `valid=False` 并写明原因。
   报告中显示为「**不可测(回放1%)**」。**宁可报"测不出来"，
   也不要一个漂亮的假结论。**
2. **要测 LLM 的成本敏感性，必须真的重跑**（花 API 额度和时间）。
   这条留给下一轮。

⚠️ 顺带纠正一条更一般的说法：**"录制/回放让 LLM 实验可零成本重跑"
只在"上下文不依赖运行路径"时成立**。凡是 prompt 里含账户/组合状态的
策略，回放都只能复现**那一条**路径——这不是回放机制的缺陷，
而是"路径依赖"这件事本身的性质。

### 顺带补上的三件事（A3 收尾时点名的 A4 前置）

1. ✅ **账户状态回流**：`run_agent_session` 把 `equity/position` 真正接上。
   A3 的验证跑批每次都看到"空仓 / 权益不变"——那只能叫"决策序列"，不算运行。
2. ✅ **区间重叠检验**：复用 `tw/analyzer_consistency.py`（承载了项目最贵的教训）。
3. ✅ **理由里的外部实体扫描**：把 A3 发现的幻觉（理由写了"标普期货与恒指期货"
   而可见状态里没有）变成**可计量的指标**。
   ⚠️ 它是**关键词启发式**，用途是"把可疑样本捞出来给人看"，不是自动判定；
   词表刻意小而准——**误报多了这条指标会被整体忽略**（与 `_is_leaky_key` 同源教训）。

### 变异验证（A4）

新增 **6 个（M85~M90）**：

| 编号 | 注入的错误 | 为什么它危险 |
|---|---|---|
| M85 | 订单在**提交的那一根**就成交 | 让订单回到过去成交 = bar 级回测最经典的未来函数 |

## 8. 诚实边界（必须先说清楚）

1. **LLM Agent 的真实收益，几乎肯定远低于演示**。这是该领域公认现状
   （77 篇研究里 0 篇可复现）。
2. **LLM 延迟不适合高频**：单次调用几百 ms 到数秒，只适合
   「每个决策窗口决策一次」（如每 N 个 tick 或每个 K 线收盘）。
3. **不能因为它说得头头是道就信**：`reason` 字段是**审计材料**，不是证据。
   证据是"扣掉成本后还赢 noop"。
4. **真钱（B 路）需要有充分验证之后才谈**，且需要单独确认（权限/额度/风控）。
5. **Agnes 通道的可用性要实测**：模型名、配额、并发限制、失败重试，
   都要在 A3 里先验证再设计流程。
