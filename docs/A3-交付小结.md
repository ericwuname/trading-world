## 3. ⭐ 真机 A/B：只换 prompt 版本，成交率差 3~5 倍

BTC/ETH 永续 1H，各 8 次决策 × 3 采样，**同一个模型**：

| | v1 BTC | v1 ETH | v2 BTC | v2 ETH |
|---|---|---|---|---|
| 解析成功率 | 100% | 100% | 100% | 100% |
| **成交比例** | **12.5%** | **37.5%** | **50.0%** | **75.0%** |
| 主动弃权 | 87.5% | 62.5% | 37.5% | 25.0% |
| 被风控拒 | 0% | 12.5% | 12.5% | 0% |
| 延迟中位 | 8.6s | 8.5s | 9.3s | 8.3s |

**v2 相对 v1 的唯一改动是提示词的形状**：
把"数据源不提供的字段"折叠成一行 + 明确告诉模型"你能从收盘价序列推断什么"。

### 为什么会这样（这是本轮最有用的一条结论）

v1 的弃权理由高频出现「资金费率为 0」「买卖盘缺失」——**真实 OHLCV 库里
本来就没有这些**。模型把注意力花在了缺失的东西上，于是"缺什么"压倒了"有什么"。

> ⇒ **在 LLM 交易里，"告诉它你有什么"比"给它更多数据"更关键。**
> 而"Agent 很保守"这个观察，很可能只是提示词没把可用信息讲清楚。

原始记录已归档 `docs/llm-run-20260921/`（96 次调用，**不含密钥**），
可直接 `--replay` 复核。

### ⚠️ 三条边界（必须同时说清楚，否则上面的数字会被过度解读）

1. **样本极小**（每格 8 次）。差距虽大，**不足以下统计结论**——
   按本项目测量纪律这类比较要走**区间重叠检验**，留给 A4。
2. **高成交率 ≠ 高收益**。v2 只是"更愿意动手"。收益要等 A4 与 `noop` 对照。
3. **本会话未接账户状态**（`on_record` 钩子没用上），每次决策看到都是
   "空仓 / equity 不变" ⇒ **这批数字不能当策略收益**，只是管线行为特征。

## 4. ⭐ 抓到四个真实缺陷（全部是静默型）

这一轮的价值几乎全在这里：**它们都不报错、日志看起来正常**。

| # | 缺陷 | 后果 | 怎么发现的 |
|---|---|---|---|
| ① | **回放把 N 次采样压成 1 次**（覆盖式索引） | 真实的"2 hold / 1 buy"变成"3 buy"——**多数派方向整个反过来**，而覆盖率仍显示 100% | **逐条比对 live/replay**（看汇总数字永远发现不了） |
| ② | **`decision_id` 跨会话永远对不上**（`run_id` 带墙钟时间） | 「回放能否核对」**从构造上不可能成功**——而那是回放存在的唯一理由 | 核对 ID 时发现全不一致 |
| ③ | **`parse_ok` 判据错** | ①只看第一次采样 ⇒ "失败但没说为什么"的记录；②改看最终 `parsed` 后，`majority_sample` 造的**兜底 hold** 让"全失败"被读成"成功" | 真机日志里出现 `[解析失败]` 但理由正常 |
| ④ | **四舍五入被算成"风控干预"** | 模型照抄 17 位有效数字的建议量、取整后超限 ⇒ `resized_frac` 被污染，**给风控记假功劳** | 对比 `requested.sz` 与 `resized_to` 的差值只有 1e-5 |

**两条可复用判据**（已沉淀）：
- **"覆盖率 100%"只说明"找到了"，不说明"找对了"。** 摘要级指标
  （覆盖率/成功率/成交率）无法发现"取错了哪一条"这类错误。
  唯一有效的手段是**逐条比对**。
- **正确性与归因是两件事。** 量**确实**被夹了（正确性不能让），
  但四舍五入不算风控的功劳（归因要准）——**两个事实都要留**。

## 5. 两条实测观察（不是缺陷，但要记住）

**① 模型会引用快照里没有的外部信息（幻觉实证）**

v1/BTC 的一条决策理由写着：

> 「…且**标普期货与恒指期货均上涨**提供共振支撑」

而 `visible_state` 里**没有**任何外部市场数据，prompt 也明确写了
"不要引用任何未在快照中出现的信息"。

⇒ 这是设计文档「回放模式默认关外部访问」那条设计的**实测反面证据**：
**提示词挡不住训练知识**。它不会"上网"，但它会**记得**。
⇒ 评估时必须把"Agent 的决策依据**不可完全审计**"列为已知边界。
（A4 可加一个"理由里提到的实体是否在可见状态中"的自动扫描。）

**② 数据源缺字段会直接改变 Agent 的行为**

见 §3。⇒ **给 LLM 看的数据，"缺了什么"要和"有什么"一样被显式管理。**

## 7. 一件顺手做的安全改进

原来 key 只能从环境变量读，实践上意味着要 `export AGNES_KEY=...`——
**key 会进 shell 历史、进进程表**，而且每次运行都要重粘。

现在支持第三顺位：**`~/.workbuddy/secrets/<provider>.json`**（仓库外）。
本项目对 OKX 凭证已经用这条约定，LLM key 沿用同一条。

- 查找顺序：`api_key` 参数（测试注入）→ 环境变量 → secrets 文件
- `.gitignore` 已加 `secrets/`、`.env`、`*.key` 等兜底规则
- 异常信息里**只出现变量名与文件路径，不出现 key**
- ⚠️ **已确认仓库内无任何密钥**（也扫过归档的 96 条记录）
